# Rails 8 API Authentication — v1.0.0 Release Hardening Design

Date: 2026-09-08
Status: Approved direct-stable design
Target branch: `release/v1.0.0`
Base: `main` at `dbb33261ca274064f93f58cf8bdfe24092d22452`

## 1. Purpose

Prepare `dangkhoa2016/Rails-8-API-Authentication` for its first public semantic-versioned stable release without adding new authentication features or rewriting the established PostgreSQL and SQLite baselines.

The release-hardening track must provide a reproducible, fail-closed path from one exact source candidate to stable `v1.0.0`, with CI, published-artifact verification, provider deployment evidence, repository controls, and explicit acceptance records.

## 2. Frozen baseline invariants

These historical source lines remain immutable:

- `baseline/sqlite-v1` at `1d842b18c1d1b07c027cbb7d49c19a52d16f98bc`

No baseline branch, baseline tag, or baseline release is rewritten by this work.

## 3. Release model

The first public semantic-versioned release is direct stable:

```text
main @ dbb3326
    |
    +-- release/v1.0.0
            |
            +-- repository hardening
            +-- release contract
            +-- verification tooling
            +-- provider deployment recipes
            +-- compatibility corrections
            +-- acceptance evidence
            |
            +-- reviewed pull request -> main
                    |
                    +-- v1.0.0
```

There is no public prerelease tag prerequisite. `v1.0.0` is created only after all mandatory gates PASS on an explicitly accepted implementation candidate.

## 4. Scope

### Repository hardening
- CI covers pull requests, manual dispatch, and pushes to `main`.
- Existing security, lint, Ruby/PostgreSQL matrix, custom JWT-header, schema-load, and coverage behavior remains intact.

### Release contract
- `CHANGELOG.md` records pre-1.0 milestones and first-release engineering.
- `docs/RELEASE_PROCESS.md` and `.vi.md` define fail-closed stable-release gates.
- `docs/releases/v1.0.0-acceptance.md` records observed acceptance evidence only.

### Verification tooling
Repository-owned scripts must:
- resolve/report exact source state;
- verify frozen GHCR variants and architecture aliases;
- validate repository contracts;
- run deployment health and authentication smoke;
- return non-zero on mandatory mismatch or failure.

### Deployment portability
Beam.cloud uses the immutable PostgreSQL baseline image by default and supports `JWT_AUTH_HEADER=X-Authorization` for the provider transport workaround. Hugging Face Spaces uses the SQLite baseline for a self-contained demo. Neither recipe may contain private credentials or overstate HA, SLA, durability, or multi-tenant characteristics.

## 5. Gate model

### Gate 1 — Repository hardening
PASS requires valid CI trigger coverage, green existing jobs, and no authentication semantic changes.

### Gate 2 — Release contract
PASS requires complete EN/VI release documentation, changelog, deterministic verification tooling, and no unresolved mandatory placeholder.

### Gate 3 — Published artifact verification
PASS requires frozen PostgreSQL and SQLite branch/tag/source/platform verification for amd64 and arm64.

### Gate 4 — Deployment portability
PASS requires sanitized provider recipes, explicit runtime-secret contracts, and truthful provider limitations.

### Gate 5 — v1.0.0 readiness
PASS requires on one exact implementation candidate:
- full GitHub CI PASS;
- repository verification PASS;
- GHCR verification PASS;
- at least one full real deployment smoke PASS for `/up`, `/users/sign_in`, `/user/profile`;
- repository controls reported active;
- observed-value acceptance evidence recorded;
- no known release blocker.

`NOT RUN` and `BLOCKED` are never equivalent to PASS.

## 6. Runtime provenance

The accepted source candidate and provider runtime image provenance must be stated separately. The Beam recipe intentionally wraps frozen image `ghcr.io/dangkhoa2016/rails-8-api-authentication:postgresql-6897c77`, whose source baseline is `6897c773ec1321401e52c21c63870a72d01ca349`.

A successful Beam smoke proves the documented deployment tooling and provider JWT transport path against that frozen application runtime. It must not be described as proof that the application container itself was built from the stable source candidate unless such an image was actually built and observed.

## 7. Git history and evidence lineage

Keep logical implementation changes separate rather than squashing unrelated concerns. The intended release history preserves distinct commits for repository hardening, compatibility correction, Beam deployment tooling, Beam secret semantics, and final evidence.

The acceptance-evidence commit is evidence-only. The acceptance document records the exact implementation SHA that was qualified before the evidence commit. Rewording or evidence-only changes must not silently redefine runtime provenance.

## 8. Repository policy

Target controls:

- `main`: PR required, mandatory CI checks required, force pushes blocked, deletion blocked.
- both baseline branches: force pushes blocked, deletion blocked.
- no bypass actors.

Controls are PASS only when GitHub reports them active.

## 9. Publication

After Gate 5 PASS and reviewed merge:

1. verify merged `main` and frozen artifacts;
2. create annotated tag `v1.0.0` on the accepted implementation commit recorded by the acceptance document;
3. publish a non-prerelease GitHub release;
4. run post-tag GHCR verification and deployment health verification.

The tag is immutable after publication. Any post-publication source correction requires a subsequent semantic version.

## 10. Non-goals

This track does not:
- add authentication features;
- redesign Devise/JWT/RTR semantics;
- rewrite baseline history or tags;
- promise HA/SLA/durability for demo providers;
- commit secrets;
- require an unnecessary public release-candidate phase.

## 11. Success definition

The release track succeeds when an exact implementation commit is fully qualified, evidence is recorded without ambiguity, repository controls are active, the reviewed change reaches `main`, and immutable stable tag `v1.0.0` is published with truthful source/artifact/deployment provenance.
