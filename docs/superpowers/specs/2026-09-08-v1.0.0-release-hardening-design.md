# Rails 8 API Authentication — v1.0.0 Release Hardening Design

Date: 2026-09-08
Status: Approved design; implementation pending review gate
Target branch: `release/v1.0.0-rc.1`
Base: `main` at `dbb33261ca274064f93f58cf8bdfe24092d22452`

## 1. Purpose

Prepare `dangkhoa2016/Rails-8-API-Authentication` for its first stable release without adding new authentication features or rewriting the two established database baselines.

The release-hardening track must turn the current pre-v1 state into a reproducible, fail-closed release candidate process with explicit CI, Docker, deployment, documentation, and acceptance gates.

## 2. Frozen Baseline Invariants

The following source lines are historical baselines and are not modified by this work:

- `baseline/sqlite-v1` at `1d842b18c1d1b07c027cbb7d49c19a52d16f98bc`

The following immutable baseline tags/releases remain unchanged:

- `baseline-postgresql-v1` / PostgreSQL Baseline v1
- `baseline-sqlite-v1` / SQLite Baseline v1

The release-hardening work happens on `release/v1.0.0-rc.1` and is merged into `main` only after all required gates pass.

## 3. Release Model

The release lifecycle is:

```text
main @ dbb3326
    |
    +-- release/v1.0.0-rc.1
            |
            +-- repository hardening
            +-- release contract
            +-- verification tooling
            +-- provider deployment recipes
            +-- acceptance evidence
            |
            +-- pull request -> main
                    |
                    +-- v1.0.0-rc.1
                            |
                            +-- RC acceptance
                                    |
                                    +-- v1.0.0
```

A stable `v1.0.0` tag must never be created directly from an unqualified commit. It requires an accepted RC built from the same release contract.

## 4. Scope

### 4.1 Repository hardening

Update `.github/workflows/ci.yml` so CI runs on:

- `workflow_dispatch`
- `pull_request`
- `push` to `main`

Existing security, lint, PostgreSQL matrix, custom JWT header, schema-load, and coverage semantics remain unchanged unless a compatibility correction is required by the existing workflow.

### 4.2 Release contract

Add repository-owned release documentation:

- `CHANGELOG.md`
- `docs/RELEASE_PROCESS.md`
- `docs/RELEASE_PROCESS.vi.md`

The release process defines:

- release candidate naming and source requirements;
- required CI checks;
- Docker/GHCR verification requirements;
- deployment acceptance requirements;
- release-blocking failures;
- rollback expectations;
- stable-release promotion criteria.

### 4.3 Verification tooling

Add deterministic, fail-closed verification scripts under `scripts/`.

Required responsibilities:

1. Resolve and report the exact source SHA.
2. Verify expected GHCR tags for PostgreSQL and SQLite.
3. Verify multi-platform support for `linux/amd64` and `linux/arm64`.
4. Verify architecture aliases where published.
5. Run HTTP health checks against a caller-supplied deployment URL.
6. Run a minimal authentication smoke flow when credentials/test inputs are explicitly supplied.
7. Exit non-zero on any required mismatch or failed mandatory check.

The scripts must not silently skip mandatory release checks. Optional checks must be explicitly labeled optional and may only be skipped when the release contract allows it.

### 4.4 Deployment portability

Integrate sanitized deployment recipes instead of copying previous provider bundles wholesale.

Provider-specific material must not contain:

- Rails master keys;
- `production.key`;
- encrypted credentials intended for a private deployment;
- API tokens;
- database passwords;
- account identifiers or other secrets.

#### Beam.cloud

Document the previously proven custom JWT transport-header compatibility through `JWT_AUTH_HEADER`, using a PostgreSQL-oriented deployment recipe.

The repository must keep Beam-specific behavior outside application business logic. `JWT_AUTH_HEADER` remains the generic application-level mechanism.

#### Hugging Face Spaces

Provide a SQLite-oriented deployment recipe suited to a self-contained demo environment. Persistent-storage limitations must be documented explicitly; the recipe must not imply production-grade durability when the target environment does not provide it.

### 4.5 Documentation integration

Update README/documentation links so users can discover:

- database variants and baseline model;
- Docker image documentation;
- release process;
- Beam deployment recipe;
- Hugging Face Spaces recipe.

Documentation must preserve the repository's existing English/Vietnamese convention where the touched document category already follows that convention.

## 5. Branch and Repository Policy

Target policy after the release-hardening changes are merged:

### `main`

- require pull request before merge;
- require CI status checks;
- block force pushes;
- block deletion.

### `baseline/postgresql-v1`

- block force pushes;
- block deletion.

### `baseline/sqlite-v1`

- block force pushes;
- block deletion.

The current GitHub integration cannot administer branch protection/rulesets. Therefore the implementation must produce exact documented settings and verification steps, but must not claim those controls are enabled until GitHub reports them enabled.

## 6. Acceptance Gates

### Gate 1 — Repository hardening

PASS requires:

- CI trigger coverage includes push to `main`;
- existing CI jobs remain syntactically valid;
- no authentication feature semantics are changed.

### Gate 2 — Release contract

PASS requires:

- changelog exists and accurately describes pre-v1 milestones;
- release process exists in EN/VI;
- RC and stable promotion criteria are explicit;
- no placeholder or ambiguous mandatory step remains.

### Gate 3 — Verification

PASS requires:

- verification scripts are executable and documented;
- expected Docker variants/tags are explicit;
- multi-arch checks cover amd64 and arm64;
- failure conditions return non-zero;
- scripts do not embed secrets.

### Gate 4 — Deployment portability

PASS requires:

- Beam recipe is sanitized and documents `JWT_AUTH_HEADER` usage;
- Hugging Face Spaces recipe is sanitized and SQLite-oriented;
- neither recipe contains private deployment credentials;
- provider limitations are stated without overstating durability or availability.

### Gate 5 — RC readiness

PASS requires:

- all repository checks pass on the exact candidate commit;
- Docker verification passes for both database variants;
- at least one documented deployment acceptance path passes for the candidate;
- release checklist is complete;
- no known release-blocking issue remains open.

Only after Gate 5 passes may `v1.0.0-rc.1` be created.

## 7. Stable v1.0.0 Promotion

`v1.0.0` may be created only when:

- `v1.0.0-rc.1` has completed the documented acceptance process;
- no release-blocking regression has been found;
- stable release notes are finalized;
- the stable tag points to an explicitly reviewed commit;
- Docker and deployment evidence correspond to that release lineage.

If the RC requires source changes, create a subsequent RC rather than silently retagging an accepted RC name.

## 8. Error Handling and Fail-Closed Rules

Release verification must fail when:

- an expected GHCR tag is missing;
- a required platform manifest is absent;
- a health endpoint is unreachable or returns an unexpected status;
- an explicitly requested authentication smoke test fails;
- source revision evidence does not match the candidate under test;
- mandatory CI is red or unavailable;
- a required deployment acceptance condition is not demonstrated.

The release process must distinguish `NOT RUN`, `BLOCKED`, `FAIL`, and `PASS`; `NOT RUN` and `BLOCKED` are never equivalent to `PASS`.

## 9. Testing Strategy

Implementation testing is layered:

1. Static validation of YAML and shell/Ruby syntax where applicable.
2. Existing CI suite: Brakeman, bundler-audit, RuboCop, repository policy, Ruby/PostgreSQL tests, custom JWT-header tests, schema-load verification, coverage artifact generation.
3. Docker metadata/manifest verification against GHCR.
4. Container/deployment health smoke tests.
5. Minimal authentication smoke flow for an explicitly configured test deployment.

No stable-release claim is made from documentation-only validation.

## 10. Non-Goals

This track does not:

- add new authentication features;
- redesign Devise/JWT/RTR behavior;
- rewrite baseline branch history;
- move baseline tags;
- migrate production data between SQLite and PostgreSQL;
- promise HA, SLA, or persistent durability for demo hosting providers;
- commit private deployment credentials;
- automatically enable GitHub administration controls that the active integration cannot modify.

## 11. Implementation Order

1. Create `release/v1.0.0-rc.1` from the current `main` candidate base.
2. Harden CI trigger behavior.
3. Add changelog and release-process documentation.
4. Add verification tooling and tests/validation.
5. Add sanitized Beam and Hugging Face deployment recipes.
6. Integrate documentation navigation.
7. Run repository and Docker verification.
8. Open a pull request to `main` with evidence.
9. Apply/verify GitHub ruleset or branch-protection settings using an authorized administrator path.
10. Create `v1.0.0-rc.1` only after Gate 5 PASS.
11. Promote to `v1.0.0` only after RC acceptance.

## 12. Success Definition

The work is complete when the repository has a documented and executable path from an exact source commit to an accepted `v1.0.0` release, with both SQLite and PostgreSQL artifacts verifiable, provider deployment paths documented without secrets, and every mandatory release gate represented by explicit evidence rather than assumption.
